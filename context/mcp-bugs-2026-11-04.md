# MCP bugs found by the owner, 2026-11-04

Reported against the Pace MCP server (`apps/api/src/mcp/`). Not fixed yet. Per CLAUDE.md each one
needs a class in `bug-lessons.md`, a sweep, and a guard when it is fixed.

## 1. `list_project_tasks` drops tasks: the body shows 5 rows, the header counts all
- Project Algebra (`01M51JGEG038M9X8MDZ151MNP0`) has 6 open tasks. Header: `Algebra: 6 open tasks`;
  the list has 5 rows (ДЗ-8, ИДЗ-1, ДЗ-4, ДЗ-5, ДЗ-6). ДЗ-7 (`01M6JZJ5FN1QE282396KH6SQV6`) is missing.
- Stable on repeat. The task is alive: `get_task` returns it, and `SELECT … FROM tasks WHERE
  project_id=…` returns 6 rows. The one missing is the last in `ORDER BY due_at` (sixth), not a random one.
- Calculus 2 has two tasks and shows both, so it depends on the count, not the task type.
- Suspect: a `limit 5` / `slice` in the render of the open section that the counter does not share.
- Expected: show all rows, or state the cut ("showing 5 of 6") with a way to page.

## 2. `due_at` is stored in two formats, so string order is wrong
- Old ИДЗ-1: `2026-11-07T15:10:00.000Z`; new tasks: `2026-11-07T15:10:00Z`. In a string sort `.` < `Z`,
  so ИДЗ-1 lands before tasks with the same deadline. Wherever deadlines are compared as strings
  (SQL `ORDER BY`, the tool's sort, `query_sql`), order and comparisons drift.
- Fix: normalise to one format on write (and migrate the old rows); compare as instants. Probably
  related to bug 1 (the order of the cut-off rows).

## 3. `update_task` cannot detach a task from its project
- `projectId` accepts only a string; `null` is rejected. The owner had to recreate three tasks
  without a project and roll the old tasks and projects back with `revoke`.
- Fix: allow `projectId: null` in `update_task` (the endpoint schema in `packages/core`, the tool's
  input, the materializer's `task.updated`). Also odd that there is no other way out.
