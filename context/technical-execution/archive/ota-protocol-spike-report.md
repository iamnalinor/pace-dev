## Protocol and verification contract

Implement Expo Updates v1, not the app API's endpoint protocol. Negotiate Android/runtime/Accept and signing request headers; respond with protocol version 1 and structured-field version 0. JSON manifest responses cannot carry directives; multipart/mixed supports named manifest/directive/extensions parts and part signatures. Unknown-runtime no-update can use a header-correct 204 without content type; unsupported negotiation needs 406, while storage failures remain errors. Asset digests are unpadded base64url SHA-256; signatures use ordinary base64. [Protocol specification](https://docs.expo.dev/technical-specs/expo-updates-1/).

Exact pinned Android implementations:

- `codesigning/{CodeSigningAlgorithm,SignatureHeaderInfo,CodeSigningConfiguration}.kt`: `rsa-v1_5-sha256`, Java `SHA256withRSA` (RSA PKCS#1 v1.5), UTF-8 manifest/directive body bytes, structured dictionary `sig`, `keyid`, `alg`; key ID defaults to `root`. Match configured metadata rather than inventing a header format. Missing signatures fail unless unsigned manifests were explicitly enabled; keep that native option false.
- `loader/FileDownloader.kt`: parses multipart/JSON, validates signatures before accepting manifests/directives, processes optional certificate-chain parts, and requests `Expo-Protocol-Version:1`, Android platform, runtime and `expo-expect-signature`. `manifest/ExpoUpdatesUpdate.kt` requires a UUID, reads createdAt/runtime/assets, and performs safe asset filename checks. Publisher validation must be stricter than native leniencies such as its fallback date on malformed createdAt.
- `UpdatesConfiguration.kt`: trusted certificate and publisher request headers are native configuration. Keep publisher URL/channel/certificate independent of the selected account server, unsigned allowance false, and anti-bricking protections enabled. The certificate belongs to runtime compatibility, including during rotation. [Signing documentation](https://docs.expo.dev/eas-update/code-signing/).

Keep the exact serialized manifest bytes immutable through signing, object storage and serving. Later local fixtures can independently verify with `node:crypto` and WebCrypto `RSASSA-PKCS1-v1_5`/SHA-256; their success is cryptographic evidence, **not** Android parser/network interoperability.

## Fingerprint risks to resolve with fixtures

1. **Git-dependent config changes JS-only fingerprints.** `apps/app/app-version.ts` embeds commit distance/SHA in development `version`, and uses commit-time hours for `versionCode`. The fingerprint's default skips do not omit Expo config versions. Compare APK/publisher using a stable, recorded native build configuration; prove the desired JS-only result before choosing any normalization. Do not solve this with a reduced native-file allowlist.
2. **Certificate bytes need explicit proof.** Installed `sourcer/Expo.js` lists external fonts/icons/Google services files, but no signing-certificate file. Config loading tracks required modules, not arbitrary `fs.readFile` inputs; the config plugin reads certificate bytes later to embed them. A same-path certificate replacement must demonstrably change the managed runtime fingerprint. If it does not, add the certificate as an additive fingerprint source used identically by APK and publisher, rather than ignoring other sources.
3. **Local native module coverage is plausible, not proved.** Android autolinking hashes each resolved module project `sourceDir`; assert the actual source list includes `modules/pace-native/android` and imported runtime config plugins. A swallowed autolinking/config-loader error can omit sources, so reject incomplete evidence rather than accepting a hash alone. Default modern Expo autolinking uses Node, not the fallback `npx react-native config` path; keep future commands Bun-only and fail if the wrong branch is selected.
4. **Reproducibility is part of compatibility.** Pin Bun 1.4.2, Node/toolchain, lockfile, workflow and environment for APK and publisher. SDK 57's patched-package fingerprint tags can vary with Bun version. Preserve default sources/ignores until concrete paired clean-install fixtures establish a necessary exception. [Fingerprint API](https://docs.expo.dev/versions/latest/sdk/fingerprint/), [Bun guidance](https://docs.expo.dev/guides/using-bun/).

## Rollback and startup: required brief corrections

The original brief's “crashes on start → embedded bundle” is too broad. Pinned `errorrecovery/ErrorRecoveryHandler.kt` attempts remote recovery and cached relaunch before its final crash path. First `CONTENT_APPEARED` removes cached/new relaunch tasks; `ErrorRecovery.kt` removes its handler ten seconds later. Previously successful updates and post-render failures therefore require distinct cases. Preserve event/outbox compatibility across both forward and rollback bundles; automatic code rollback cannot undo persisted data. [Recovery documentation](https://docs.expo.dev/eas-update/error-recovery/).

`selectionpolicy/LoaderSelectionPolicyFilterAware.kt` accepts a compatible newer `commitTime`; `LauncherSelectionPolicyFilterAware.kt` selects the newest matching cached update. Pointing a channel at an older UUID/date is not a reliable rollback. Repackage old code/assets as a **new signed update UUID with a newer createdAt**, or use the signed `rollBackToEmbedded` directive with an appropriate newer commitTime and matching filters. Keep immutable prior releases; never rewrite their manifests. Verify both routes later against the pinned client.

Public coordinator APIs are `checkForUpdateAsync`, `fetchUpdateAsync`, `reloadAsync`, `readLogEntriesAsync`, and native-reported `updateId`, `runtimeVersion`, `createdAt`, `isEmbeddedLaunch`, `isEmergencyLaunch`, `emergencyLaunchReason`. Handle rollback results explicitly. `WIFI_ONLY` controls automatic launch checks, not all later JS-triggered downloads; an injected network decision must gate foreground downloads and conservatively skip unknown/metered states. `NEVER` disables automatic checks, including recovery fetching; `ON_ERROR_RECOVERY` retains a native recovery path. Choose that policy explicitly against the hourly/Wi-Fi requirement. `reloadAsync` is a JS/runtime reload, not the native cold process restart used for Firebase rotation.
