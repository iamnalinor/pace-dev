# Task 3 design. Stage the Firebase pair before strict enforcement

**Implementation mapping.** The local CLI in design section 3a was delivered as implementation Task 3. The remaining runtime guard and client error recovery from design section 3a, together with deployment work from design section 3b, are pending implementation Task 3b.

**Decision.** Implement the local validation and error path first. Keep existing deployments in additive mode while the version staging path is prepared and tested. Strict enforcement and removal of baked APK Firebase config are separate release steps.

## 3a. Local validation, opt-in guard and error recovery

| Surface | Change |
|---|---|
| `scripts/check-config.ts`, root `package.json`, script tests | Add `bun run check:config`. Read only the two supplied Firebase environment values and call Task 2's `validateFirebaseConfig`. A valid pair and deliberate absence pass. Invalid JSON, invalid shape, a partial pair and project mismatch fail with exit 1 and one fixed reason code. CI additionally supplies an expected state (configured or disabled) so two missing inputs cannot pass a configure operation. Use explicit env inputs in CI and disable implicit dotenv loading. This command checks its inputs only. |
| Core API contract, Worker env/app/FCM | Define a shared Firebase reason schema and `{code:"server/misconfigured",message:"Server configuration is invalid",reason}` response. Add a rollout binding such as `PACE_FIREBASE_CONFIG_POLICY` with explicit `additive` or `strict`. Unset is additive during migration. Reject an unknown supplied policy at preflight. Validate against request env, with a per-env and value-aware cache if warranted. With strict enabled, mount the guard after CORS and before protocol/auth on application requests to `/api/*`. Health and instance must return the same 500 on invalid config. Keep preflight OPTIONS readable to the web and preserve behavior on non-API paths. FCM's Worker/DO send path must share the verdict and never send against an invalid pair in strict mode. Preserve the valid legacy sender in additive mode. |
| `packages/client/src/api-client.ts`, `instance.ts`, server feature and i18n | Decode a whitelisted optional reason only for HTTP 500 and code `server/misconfigured`. Preserve it in a discriminated instance error. An unknown future reason gets generic configuration-error copy. Keep generic 5xx unreachable and preserve 404/version behavior. Use a separate origin-scoped configuration error in `server-store.ts`. Show localized reason via the existing signed-out server area and Change server refusal, and the signed-in status surface with a retry. Reuse the existing server check for retry/foreground. A successful same-origin check clears the status, an old-origin answer cannot overwrite it, and no user is sent to the versions screen or signed out. Retain local data and the outbox during the failure. |
| `docs/self-hosting.md`, deployment notes, bug lessons | Document exact CLI inputs and reason output, the transition from service-account-only, safe pair lifecycle and intentional exceptions for optional settings. Keep the LLM, Telegram and origins audit narrow. Name which existing fallbacks are deliberate. No baked APK changes in this task. |

**Proof for 3a.** RED/GREEN tests cover every reason and no secret fragments in CLI output. workerd tests cover correct pair, neither, both partial cases, malformed both ways and mismatches under both policies. Pin health, instance, auth, a protected endpoint, stale protocol, preflight, no unauthorized FCM sends, request env isolation and recovery. Client/app tests distinguish typed 500, generic 500 and 404; cover signed in and out, Change server, retry recovery and stale-origin response. A real targeted run uses a local Worker with a deliberately mismatched fake pair and checks that a normal matching/disabled restart recovers. Use an independent Sol or cheaper reviewer when runnable.

## 3b. Deployment preflight and immutable promotion

Keep automatic CI on its existing additive route until an isolated Cloudflare rehearsal succeeds. Add the guarded route behind an explicit production environment variable or protected manual input. On activation, all automatic deploys for that Worker use the guarded route. A strict Worker must never silently fall back to the legacy route on a missing flag or failed preflight. A rollback is a specific recorded version operation.

1. **Preflight before remote D1 changes or traffic movement.** Check exact checkout SHA, account and Worker name. Use the Worker API to distinguish authenticated, confirmed existing and confirmed absent from auth/network failures. Require a clean single active version for the first rollout and capture that ID for rollback. Run `check:config` against supplied inputs for configure/rotate. Treat the secret listing as names only, including if the GitHub secrets are absent. A local both-unset result says nothing about a deployed Worker.
2. **Stage one candidate and verify its effective bindings.** For existing Workers, use `wrangler versions upload` with a unique tag and a non-secret attempt marker, and keep the version inactive. Supply `--secrets-file` only in configure/rotate, with both values written to a temporary mode-0600 JSON file and removed in a trap. Use explicit GitHub secret names. Map `GOOGLE_SERVICES_JSON` to `FIREBASE_ANDROID_CONFIG` at the workflow boundary and use the same validation for both. Disable performs a single staged bulk removal after the candidate upload as described below. A normal upload with no file keeps previous secret bindings, so omission never disables push. Use a protected, exact Version URL for the candidate and match its real Worker version ID via the Cloudflare version metadata binding, attempt marker, requested policy, and effective mode from strict health or a sanitized readiness response. Return only fixed verdict/reason, mode, and version identity. Confirm protected Version URL access is configured and the unauthenticated URL is denied before relying on it. Use read-only health and instance requests because this version uses the target Worker's bindings.
3. **Promote only the verified version.** Reconfirm the active deployment and staged IDs have not drifted. Apply only required backward-compatible D1 migrations, then run `wrangler versions deploy <verified-version-id>@100% --yes`. Re-probe production health and instance, assert expected mode and version, and observe legacy FCM on a controlled device before removing baked configuration. A failed preflight or candidate probe leaves traffic unchanged. A post-promotion failure rolls traffic back to the recorded verified compatible version. Version rollback does not undo D1 or DO data/migrations. Remove the independent post-deploy `FIREBASE_SERVICE_ACCOUNT` write. Verify the remaining Telegram/LLM steps preserve the pair and repeat the production smoke after any of those steps that create a new Worker version. Apply trigger changes only if explicitly needed and validated, since upload/promotion does not replace ordinary trigger management.

| Operator intent | Required input and behavior |
|---|---|
| Keep, default | Do not read or rewrite Worker-only secret values. Require the latest version to equal the active baseline before upload, or stop for drift resolution. Check the effective state on that baseline through readiness first, then require the same state and public project identity on the inherited candidate. A legacy sender-only, malformed or unverifiable baseline stops strict activation. No silent conversion to disabled. |
| Configure or rotate | Explicit protected dispatch and both GitHub-supplied values. Validate before upload and upload both together with the new code. Require candidate proof of configured state and the expected public project. Treat real FCM authentication/delivery as a separate smoke. A cross-project rotation intentionally makes older baked APKs unable to receive FCM for that server, so schedule it with client migration or explicitly document polling during that transition. |
| Disable | Explicit protected dispatch. Stage a base candidate, then pipe both keys set to JSON null into `wrangler versions secret bulk` to produce a second inactive version. The pinned Wrangler patches the latest version, so require the first candidate to be latest, serialize all deployment and secret writes, and verify the returned second candidate has this run's unique marker and effective disabled state. If the pair is already absent, skip removal after verifying that state. Stop on drift, including a parallel upload. Never use two live `secret delete` calls. |
| Fresh Worker or pending DO migration | `versions upload` cannot bootstrap pending DO migrations. Use a separate explicit bootstrap/migration run while policy is additive, with known local inputs for either a full valid pair or deliberate disabled state. For first configure, use ordinary `wrangler deploy --secrets-file` to upload both with the Worker. For a freshly confirmed Worker with deliberate disabled state omit the file. For an existing Worker requiring a DO migration, use the already verified effective mode with no simultaneous change of pair, or stop for a separate staged pair change. Probe deployed additive health and readiness, then use the existing-Worker staging path for strict activation. No automatic fallback from staging failure to ordinary deploy. |

Use one production concurrency group for all pair operations and treat out-of-band secret/deploy changes as a drift failure. The current workflow runs API deploy before its Firebase secret write and several other post-deploy writes. Keep the new route isolated until its ordering and invariants are covered. In self-hosting docs give the equivalent steps for a worker whose values are maintained outside GitHub. An operator who cannot securely probe the exact candidate keeps the additive mode until they can do so.

## Tests and release evidence

- Fake CLI/HTTP tests assert command order and that D1 and promotion never run after invalid inputs, absent or mismatched candidate identity, non-OK health, active-version drift, authorization failure, missing expected configured pair, or partial response. Keep preserves a Worker-only pair and rejects a legacy partial pair for strict activation. Configure writes both once. Disable creates an inactive removal candidate for both. Confirm temporary files are restricted and removed even after a failure. Test duplicate workflow runs and cleanup/retry after an inactive candidate was left behind.
- Check checked-in workflow lint and pinned Wrangler help/behavior locally. Rehearse an existing Worker and a fresh DO-bound Worker on a non-production Cloudflare target before enabling the route for Pace. Prove protected Version URL availability, exact version binding identity, both-value rotation and removal, final health, rollback and real FCM on the intended app. Confirm token permissions, protected environment and absence of direct concurrent edits. A failed upload or missing privilege is a blocker, never a reason to weaken the gate.
- Ship Task 4 only after deployed server readiness and device verification. Any rollout flag is transitional, with removal/default-strict as a later task after supported deployment paths migrate. Keep the original global loud-failure requirement as the final behavior.

**PM risk verdict.** Build the local slice. Validate first on deployment activation. The primary risk is locking out every API caller because locally valid inputs and the effective Worker bindings diverge. Existing workflow ordering and pinned Wrangler source demonstrate that risk. Pair values on live Workers, Access, account permissions, deployment results and device push remain unverified. The decisive test is an isolated rehearsal where an invalid inherited pair fails before traffic moves and both a valid matched pair and deliberate disable can be promoted by exact version.
