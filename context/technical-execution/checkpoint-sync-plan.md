# Task 9C: Checkpoint Sync and Complete History Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans task-by-task. This packet defines a cohesive implementation; it is planning only and does not authorize production pruning. Read the Task9A/9B implementation handoff before editing their files.

**Goal:** Start a fresh or stale device from a validated checkpoint plus cursor tail, retain ordinary offline actions and pending writes, and provide correct complete History, historical board, export and historical edits.

**Architecture:** A checkpoint seeds full current CoreState while explicit coverage describes which source envelopes are resident. Local stores install bootstrap/page/history changes in guarded transactions. Full-source consumers share one demand-driven hydration operation, after which the client uses normal complete-log replay. Server source and archives remain intact; legacy sync remains available.

**Tech Stack:** Bun, TypeScript, Zod, Zustand, Vitest, workerd/SQLite/R2 through Task8 ports, Expo SQLite, IndexedDB/idb, React Native, Playwright.

**Spec:** tasks-8-9-plan.md9C; checkpoint-design.md; checkpoint-persistence-plan.md; context/technical-execution/archive-plan.md; revised T5c in context/technical-roadmap.md; AGENTS.md; docs/architecture.md/testing.md. No exploratory QA, Android run, deployment, production config, pruning or minimum-protocol activation.

## Global constraints and fixed decisions

- Existing `Checkpoint` is format1: version, storeId, build, coveredSeq, cutoff, cutoffTimezone, state, eventIds/eventCount, correctionTargets, lastEffective(occurredAt+id). Reuse `parseCheckpoint` and `replayCheckpoint`; never invent a second reducer/materializer.
- CHECKPOINT_VERSION owns representation **and replay/reducer compatibility**. Bump it on incompatible semantics. Client validates that version/schema/hash/store match; server `build` remains opaque deployment identity to the client. Server9A still checks its expected build when loading its cache. Do not add a redundant replay version or compare an APK build with a server release/schema tag.
- Keep PROTOCOL=MIN_CLIENT_PROTOCOL=MIN_SERVER_PROTOCOL=1 for this additive rollout. Additive fields/endpoints are explicitly nonbreaking in current protocol.ts. Future pruning is a separate breaking protocol2 activation, with absent/unreadable HTTP header and socket protocol-query refusal policy specified before enabling it. A minimum bump alone currently admits absent protocols.
- Existing `/api/sync/pull`, store.list and MCP export_all retain their full-source meaning. Add bootstrap; extend pull with optional pinned history bounds and checkpoint-aware negotiation. No second public export/history API is needed.
- Local `SYNC_SCHEMA_VERSION` can become2 for the storage/sync upgrade, but upgrade is transactional and preserves outbox. It is not API protocol2.
- A bounded recent row count is not bounded snapshot bytes: state, known IDs, correction targets and eventual hydrated history grow. Measure, report exceptions, never promise flat memory or wire size.
- No partial local log may be passed to historyViewModel/materializeAt/exportSheets or used as proof that an account is empty.

## Actual consumers to change

- `packages/client/src/state.ts` and `local-log.ts` assume every rebuild uses all source; persist failure, adopt and reload must rebuild from base+resident tail when partial.
- `actions/instances.ts` uses log IDs twice; replace with known IDs including revoked deterministic IDs.
- Source-origin lookups exist in task-actions.ts(delete task), series-actions.ts, inbox-actions.ts, work-actions.ts(undo submit), activity-edits.ts(origin/edit/revoke), plus state.revoke/undoLast. Hydrate before the lookup/validation, not only just before emitting a correction (otherwise a partial lookup returns an incorrect not-found).
- `view-models/history.ts` derives both raw event rows and board from full log; `react.ts` useHistory currently returns an immediate value; `screens/history-screen.tsx` must handle loading/error.
- `view-models/export.ts` takes full state.log; web ExportRow currently downloads synchronously with no caught failure. Await full history and a consistent fresh state before building sheets. Native ExportRow remains null.
- `apps/app/src/app-state.tsx` treats events.length===0 as empty; use complete known source-ID count and explicit state readiness instead.
- Day/Week/Insights/time tracking read full CoreState slices, which checkpoint includes; they do not need to download all source solely to read current projections. History's board at a past instant does.
- `bootstrap.ts` runs ensureInstances before first sync and `sync-loop.ts` repeats it on foreground. Persisted checkpoint IDs must be ready before these calls; never infer instance dedup from resident source alone.
- `peer-tabs.ts` payloads lack copy identity; BroadcastChannel is profile-wide, while local origin/session can change. A stale event payload must not cross a replaced copy.

## Contract-first server changes

**Files:** new core api/schemas/bootstrap.ts, existing api/schemas/sync.ts + instance.ts/endpoints.ts/core.ts; API app.ts/sync-routes.ts/shared contract + user-store-host.ts; user-store bootstrap/history methods; platform/cloudflare/user-store.ts forwarding. Task9A/B supply checkpoint and archive readers; do not bypass ports.

1. Add `features.historyCheckpoint` via tolerant knownOrNull literal CHECKPOINT_VERSION (unknown/absent=>null). Server advertises1 only when checkpoint bootstrap and pinned complete-source reads work. createPaceClient obtains `/api/instance` once per origin/runtime for sync negotiation, caches success, coalesces concurrent requests, and invalidates on runtime replacement; an outage is a normal failed run, not assumed legacy. Old servers =>null and existing sync behavior. No repeated discovery on every safety poll.
2. New endpoint `GET /api/sync/bootstrap?limit=200`, auth true. Output is a discriminated `kind:"checkpoint"|"source"` union. `source` explicitly means no eligible/compatible checkpoint; client uses legacy full pull without resetting pending events. `checkpoint` returns `{storeId, checkpointJson:string, checkpointSha256:string, throughSeq:number, records:SequencedSyncRecord[], seq:number, more:boolean}`. Define SequencedSyncRecord `{seq:positive int,event:SyncEventSchema}`. JSON string avoids forcing CoreState's unknown-valued overrides through actor RPC Serializable. Hash the exact UTF-8 checkpointJson bytes before parsing; validate decoded checkpoint with core parser at client boundary; transport strictness is stronger here than tolerant legacy `knownValues`.
3. One serialized actor call captures validated checkpoint, generation and current high-water H, and first tail page up to H. `checkpoint.storeId==storeId`, coveredSeq<=seq<=H. Include actual original source seq; never fabricate per-event seq from page length. If an otherwise valid stored checkpoint cannot safely replay the captured tail, produce a replacement checkpoint from retained complete source through H and return an empty tail, or explicit source mode. Do not send an unusable checkpoint and expect the fresh client to reverse reducers. First choice: replacement checkpoint, cached so repeated bootstrap is not full replay each time. The complete-day cutoff stays informational; coveredSeq may advance through H for this recovery snapshot.
4. Extend existing pull query with optional `storeId`, `through`, and `checkpointVersion:1`. These are sent only after negotiated capability1. Bound pinned reads by generation and immutable high-water. Wrong generation=>409 store/changed. Invalid through/since=>422 stable contract error. Output keeps legacy `{events,seq,more,storeId}` and adds actual `records` for enhanced calls. Pinned full history with through uses Task9B full-history reader and never returns a bootstrap demand. It reads seq0..H including archived cursor holes.
5. For enhanced **ordinary** pull without through, if since is behind the server's current usable checkpoint coveredSeq, return optional `bootstrapRequired:true` with no cursor advancement; legacy callers without capability still get actual full source. New client performs exactly one bootstrap then continues; repeated signals for an installed same cursor are an error, not a loop. Always permit an already-current/empty pull to settle.
6. Keep socket pace.v2 additive. Add optional checkpointVersion to strict pull request and optional records/bootstrapRequired to events answer. Older messages remain accepted; old clients ignore extra output. Proactive events include actual seq records for new clients (legacy events field stays); large more-only notifications simply trigger enhanced pull. HTTP and socket call the same actor methods, use the same reset/bootstrap logic and bound page sizes. Bootstrap/history hydration itself uses HTTP; no need for pace.v3 or new socket message types.
7. Extend literal Result errors and mount mappings exhaustively. Check source-mode fallback occurs only for an explicit legitimate response; corrupt transport/hash/version is a visible recoverable error, never silently installed/downgraded to empty state.

### Server RED/GREEN sequence

- [ ] RED bootstrap throughH + appended event atH+1: frozen checkpoint/tail coverH, next normal pull coversH+1 once; reset between pages refuses old storeId.
- [ ] RED unsafe suffix (correction, correction-of-correction, missing-target fulfillment, backdate, same-time lower ID) is repaired by a complete-source replacement, equal to full replay. Unknown historical schema blocks checkpoint eligibility, never disappears into a misleading snapshot.
- [ ] RED stale enhanced cursor signals once then progresses; legacy HTTP/socket pull still full source; pinned history is never redirected to bootstrap. Archive outage uses intact source as9B permits, never partial successful history.

## Transactional local persistence contract

**Files:** client/event-store.ts + new checkpoint-store-types.ts (types/helpers only); memory adapter; app platform/sqlite-event-store.ts/event-store.web.ts plus facade; held/failing test adapters; shared adapter contract tests.

Hashing must work on Hermes as well as browsers: add `sha256Text(text):Promise<string>` to PaceClientOptions (default Web Crypto when available); apps/app runtime passes its platform implementation using existing expo-crypto digestStringAsync(SHA256), factored beside session-fingerprint.ts. Do not assume crypto.subtle exists on Android. Tests pass a real SHA-256 implementation; no fake constant hash. This is the only new platform callback needed.

Add these operations; keep existing append/listPending/markSynced methods, but stop sync from coordinating metadata with separate setCursor/setStoreId calls. Add persisted `copyToken` (random identity), owner mark, checkpoint JSON/hash, coverage and source records. Keep source events and pending IDs separate as now.

- `readSnapshot(): Promise<LocalSnapshot>` atomically reads `{copyToken,owner,storeId,cursor,syncVersion,checkpoint,coverage,records,pendingIds}`. Existing full log migrates to coverage full; old tables persist intact. Do not read checkpoint/meta and records in separate independent transactions.
- `installBootstrap({guard,checkpoint,records,seq,syncVersion}): Promise<Result<LocalSnapshot,"sync/copy-changed"|"history/rebuild-required">>` is one transaction. Guard includes expected copyToken, owner, expected local storeId and maximum observed cursor, checked **inside** transaction. Keep current pending events for same confirmed generation (or first confirmed generation on the same still-owned unconfirmed copy); different non-null server generation clears old pending/source/base and creates a new copyToken. Invalidate old responses before another local write can land there. Preserve owner claim on server reset.
- `applyRemotePage({guard,storeId,since,seq,records}): Promise<Result<LocalSnapshot,"sync/copy-changed"|"history/rebuild-required">>` atomically merges server canonical envelopes, acknowledges matching pending, updates cursor, validates generation and contiguous delivery *page coverage* (not numerical gaplessness), never moves cursor backwards. Out-of-order peer already-applied pages are no-ops; a gap asks sync for a pull.
- `installHistory({guard,through,sourceRecords}): Promise<Result<LocalSnapshot,"sync/copy-changed"|"history/incomplete">>` atomically merges the validated complete source prefix throughH with then-current later synced tail and pending events, verifies all known base IDs are present through its checkpoint coverage, switches coverage full and drops base only in the same commit. No history request changes the sync cursor merely by reading old rows. Writes that landed while history downloaded survive, as do their pending markers.

Guards are persistent identity/ownership, not a revision bumped on every ordinary append; otherwise background actions starve hydration. A bootstrap computed before a newer cursor cannot replace it: return reload-needed and read the shared snapshot, rather than overwriting forward progress. copyToken changes on clear and when another owner claims the shared copy. For ordinary source updates during install, read/rebase current pending inside the transaction. If their replay needs source, return history/rebuild-required with **no partial disk change**; hydrate source, then retry.

Checkpoint eventIds prove identity, not a canonical event envelope. If a pending id overlaps base ids, hydrate its source before dropping/acknowledging it: a snapshot alone cannot reconcile recordedAt clamping or concurrent deterministic-id payload differences. Do not discard pending just because its id appears in a checkpoint. The same rule applies to server canonical replacement and failed local writes.

SQLite uses withExclusiveTransactionAsync and additive user_version migration. IDB upgrades must branch by oldVersion (current upgrade unconditionally creates stores and will fail if reused unchanged); one readwrite transaction spans all touched stores. No network/hash/decompression await within an IDB transaction: validate external data before opening it, and recheck identity inside. Hash/parse persisted data on load; invalid base with partial source cannot be rebuilt from INITIAL state as if complete. Show recoverable loading/error and hydrate/re-bootstrap; retained old valid local state remains until replacement succeeds.

## Base-plus-tail state and history coordinator

**Files:** state.ts/local-log.ts, new history.ts + focused tests, actions source-dependent files listed above, create-client.ts/client.ts, react.ts.

- Add `historyCoverage:"full"|"checkpoint"`, nullable validated base, resident sequenced records, `knownEventIds:ReadonlySet<string>` (base IDs+resident+pending), and history resource status idle|loading|failed|ready. Persist serialization as arrays/JSON, never Sets. AppState.log/events become explicitly resident-only when checkpoint coverage; current CoreState slices still include the whole checkpoint history. Base does not contain raw effective events, so never synthesize them from projection objects.
- Introduce `completeHistoryOf(state): Result<CompleteHistorySource,"history/not-loaded">`; HistorySource/export input must require the returned full-coverage type. Update fixtures accordingly. Keep all consumer access behind that guard; do not scatter casts that restore the old misleading contract.
- Replace FOLD/Memory rebuild with shared function that uses core replayCheckpoint(base,resident synced tail) then safe local pending events; full mode uses existing full materializer. Duplicate IDs use knownEventIds (including revoked/future correction targets metadata). Same-time order always uses occurredAt+id. `lastAppliedOccurredAt` alone is not sufficient checkpoint append authority.
- Persist-local failure, remote canonical adoption, reload and peer update use the same base-aware rebuild. Memory must not advance ahead of an install that has not committed; keep existing optimistic local actions/rollback behavior.
- `state.stage` is the final invariant gate: while partial, an event requiring core source rebuild is refused with literal history/not-loaded before it appears or enters pending. Direct state callers cannot bypass historical action rules. Ordinary canonically ordered noncorrection actions apply immediately offline using full current slices and known IDs.
- `PaceClient.history.ensureComplete(): Promise<Result<void,HistoryError>>` coalesces concurrent consumers, uses a pinned `{storeId,through}` high-water, pages **all** source through it via extended existing pull, verifies event/seq uniqueness, progress and checkpoint ID completeness, then installs once. It merges then-current later tail/pending at commit. It neither invokes runSync recursively nor holds the state mutation queue during network awaits. Newer unsafe remote pages wait for or join hydration; no infinite repeated same-id pulls. An invalid/unknown event in checkpoint-mode pinned hydration fails explicitly rather than declaring source complete after skipping it.
- On clear/sign-out/server replacement/close, abort hydration and invalidate every completion using runtime lifetime+copyToken+owner+generation. Loading state cannot remain forever after failure; errors keep useful current projections and offer Retry. No automatic tight retry on render or clock tick.
- Source-dependent action wrappers await ensureComplete **before** rereading state and validating intent. Ordinary actions do not hydrate. Actions needing source include corrections, undoLast/revoke, origin-based edits/delete, any event <=base lastEffective, and ordinary ids named by base correctionTargets. Offline hydration returns history/offline (or history/unavailable for other failure); no optimistic mutation/outbox entry occurs. After awaited hydration redo validation against the new state, never reuse a captured pre-await task/activity.
- ensureInstances uses knownEventIds everywhere, remains offline and never hydrates just to deduplicate. Empty-account detection uses known IDs+readiness, not resident arrays. Foreground startup waits for persisted base load before ensureInstances; it may use full current state before a network sync as today.
- Peer events add `{copyToken,storeId}` identity (and owner mark if required); ignore stale payloads. Bootstrap/hydration posts `{kind:"reload",copyToken,storeId}` after disk commit; peers reload persisted base+records atomically and do not echo. A peer message is a hint, not permission to blindly trust an old event payload. Account/server changes invalidate old work even when the token happens to be absent.
