# Contributing

Thanks for looking at Pace. It is a small personal project, but it is built so that
other people can run it and change it; issues and pull requests are welcome.

## Setup

[Bun](https://bun.sh) (the version in `.bun-version`) is the only tool you need; see the
[quick start](README.md#quick-start). `bun install` also installs the git hooks:
`bun lint` runs before every commit and `bun test:unit` before every push.

Use Bun only: `bun install`, `bun run <script>`, `bunx <tool>` — never npm, npx, yarn or
node. Two exceptions run under Node on their own: the Expo CLI and Jest, invoked through
`bun run --cwd apps/app …` (their shebangs pick Node; never `bun --bun`).

## Workflow

1. **Test first.** A behaviour change starts with a failing test at the right level
   ([docs/testing.md](docs/testing.md)): pure logic in `packages/core` → Vitest (fast-check
   for invariants); an endpoint → an API test inside workerd; a screen → a component test
   for its logic and a Playwright journey with an axe check. Watch it fail, make it pass,
   then clean up. Never skip, weaken or delete a failing test.
2. **Lint after every change**: `bun lint` auto-fixes formatting and import order and
   reports the rest. Scoped variants (`bunx biome format --write <paths>`,
   `bunx eslint --fix --max-warnings 0 <paths>`, `bunx tsc -p <package>`) are fine while
   iterating; the full run is what CI checks ([docs/linting.md](docs/linting.md)).
3. **Keep the architecture** ([docs/architecture.md](docs/architecture.md)):
   core stays pure and immutable; the API contract is zod in `packages/core/src/api`;
   UIs never import the Worker; API feature folders share through `src/shared` only.
   dependency-cruiser enforces this in `bun lint`.
4. **Database changes**: edit `apps/api/src/shared/db/d1-schema.ts` (D1) or
   `apps/api/src/user-store/schema.ts` (Durable Object), run `bun db:generate`, review and
   commit the SQL under `apps/api/drizzle/`. Never edit an applied migration or the
   `meta/` folders by hand; `bun db:check` fails on drift.
5. **One commit per task**, message in the imperative, English. PRs run the full CI
   (lint with a clean tree, unit, api, app, e2e, audit).

## Conventions the linters enforce

- kebab-case file and folder names; no `index.ts` barrels; no default exports except
  tool configs, `worker.ts` and expo-router route files.
- Inline `import type`; relative imports with the `.ts`/`.tsx` extension inside a
  package; `#web/*` in the web app, `#app/*` in the Expo app, `@pace/core` and
  `@pace/client` across packages.
- zod 4 for every schema; `Result<T, E>` with string-literal error codes instead of
  throwing in pure code; exhaustive `switch` without `default`.
- Limits: 60 lines per function (80 in React components), 300 per file, complexity 10,
  3 parameters, explicit return types on exported non-component functions.
- Every `eslint-disable` carries `-- <reason>`; never relax a rule to get past it.
- Every user-visible string goes through `t()` from `@pace/core`; add new keys to
  `packages/core/src/i18n/en.ts` **and** `ru.ts` (a test checks parity). Code, comments
  and identifiers are English.
- Design values come from `packages/core/src/design/tokens.json`; `bun lint` regenerates
  the web CSS variables. Icons are generated by `bun scripts/generate-icons.ts`.

## Reporting bugs and proposing changes

Open an issue with what you did, what you expected and what happened; for crashes add the
platform (web/Android/bot) and the version (the tag of the APK, or the commit). For a
larger change, open an issue first so the design can be discussed before the code.

Security problems go through [SECURITY.md](SECURITY.md), not the issue tracker.
